## 작업 원칙

1. **모든 단계는 실행 가능한 산출물로 끝난다.** 반쯤 만든 것을 다음 단계로 넘기지 않는다.
2. **완료 기준을 먼저 적고 시작한다.** 애매하면 그 단계는 안 끝난 것이다.
3. **어려운 문제를 동시에 디버깅하지 않는다.** 렌더링·얼굴인식·네트워크는 각각 따로 검증한 뒤 합친다.
4. **키보드 입력은 처음부터 끝까지 살려둔다.** 얼굴 입력이 망가져도 게임은 돌아가야 디버깅이 된다.
5. 가까운 단계는 상세히, 먼 단계는 개요만 적는다. **먼 단계의 가짜 정밀도는 쓰지 않는다.**

# S0. Three.js 렌더링 품질 검증 — ✅ 통과

> **판정 결과**: 통과. 주관 기준("무섭다") 충족.
> **결론**: 기획서 §5의 웹 스택 채택이 검증됐다. Three.js로 공포 톤이 나온다.
> 남은 확인: 내장 GPU 1080p **60fps 실측치** (패널 하단 fps 표시).

### 구현 중 확정·변경된 값

| 항목 | 계획 | 실제 | 이유 |
|---|---|---|---|
| 안개 밀도 | 0.16 | **0.105** | 0.16은 4칸(12m)에서 97% 가려 그것이 아예 안 보인다. 0.105는 76%로 "안개 속 흐린 실루엣"이 된다 |
| 주 광원 | PointLight | **SpotLight** | 그림자 맵이 큐브 6면이 아니라 1장이라 훨씬 싸고, 손전등 연출에도 맞다 |
| 텍스처 | 외부 에셋 | **절차적 생성** | 프랙탈 노이즈 높이장 → albedo / normal(소벨) / roughness. 외부 의존 없이 조명·후처리부터 판정하기 위함 |

**실사 텍스처 교체는 보류한다.** 절차적 텍스처로 이미 판정을 통과했으므로 차단 요소가 아니라 마감 작업이다. S3 이후 여유가 생기면 ambientCG로 교체한다.

`spikes/spike-render.html`의 토글 패널(블룸/그레인/비네트/색수차/그림자/노멀맵/안개)은 이후 단계에서도 톤 튜닝 도구로 계속 쓴다.

# S0. 원본 계획 (기록 보존)

## 왜 먼저 하나

기획서 §5에서 Unity 대신 웹을 골랐고, Unity가 이기는 유일한 항목이 **렌더링 품질**이었다.
"격자 미로엔 Three.js로 충분하다"는 것은 아직 **가정**이다. 이 단계는 그 가정을 검증한다.
여기서 실패하면 이후 모든 계획이 무너지므로 가장 먼저 확인한다.

## 만들 것

**복도 한 구간.** 게임이 아니라 **스크린샷 한 장**이 목표다.

- 3×3 또는 5×5 격자 미로 한 조각 (직선 복도 + 코너 하나)
- 키보드로만 이동 (얼굴 인식 없음, 게임 규칙 없음)
- 복도 끝에 캐릭터 실루엣 하나 (대두 + 긴 팔다리, 박스 조합으로 충분)

## 무서운 복도를 만드는 6가지 — 구현 체크리스트

품질은 모델링이 아니라 **빛과 후처리**에서 나온다. 순서대로 중요하다.

### 1. 조명 — 이게 전부다
```js
// 환경광은 거의 0. 어둠이 기본값이어야 한다
scene.add(new THREE.AmbientLight(0xffffff, 0.03))

// 플레이어에게 붙은 광원 하나. 이것만이 유일한 빛
const lamp = new THREE.PointLight(0xffd9b0, 2.2, 9, 2)  // 따뜻한 색, 거리 9, decay 2
camera.add(lamp)
```
균일하게 밝은 씬은 절대 무섭지 않다. **보이는 영역을 좁히는 것**이 공포의 핵심이다.

### 2. 안개 — 공포와 최적화를 동시에
```js
scene.fog = new THREE.FogExp2(0x050303, 0.16)   // 기획서 팔레트의 --black
```
`density`는 **3~4칸 밖이 안 보이도록** 맞춘다. 기획서 §2.3의 조우 거리(4칸)와 일치시켜야
"안개 속에서 형체가 서서히 드러나는" 연출이 게임 규칙과 맞물린다. 덤으로 원거리 렌더를 잘라 성능도 얻는다.

### 3. 텍스처 — 균일한 회색 벽은 안 무섭다
- **normal map**과 **roughness map**이 필수다. 색상 텍스처만 쓰면 종이처럼 보인다
- 무료 CC0 소스: **ambientCG**, **Poly Haven** (콘크리트 / 회벽 / 녹슨 금속)
- `repeat`으로 타일링, `anisotropy`를 최대로 (바닥이 멀리서 뭉개지는 것 방지)

### 4. 포스트프로세싱 — "웹페이지"와 "게임"을 가르는 지점
`EffectComposer` 사용. 이거 하나로 체감 품질이 가장 크게 바뀐다.
```
RenderPass
 → UnrealBloomPass   (strength 0.25 — 광원에만 약하게. 과하면 싸구려가 된다)
 → FilmPass / 노이즈 (저조도 카메라 그레인. 공포 톤의 핵심)
 → 비네트           (화면 가장자리를 어둡게. 시야를 더 좁힌다)
 → 아주 약한 색수차  (0.001 수준. 넣었는지 모를 정도가 정답)
```

### 5. 그림자
`PCFSoftShadowMap`. 광원이 1개뿐이라 비용을 감당할 수 있다.
**복도 끝 실루엣이 바닥에 드리우는 그림자**가 이 게임에서 가장 무서운 요소가 될 수 있다.

### 6. 카메라 미세 흔들림
정지 상태에서도 아주 약한 idle sway (진폭 ~0.01, 주기 3~4초).
없으면 화면이 죽어 보인다. 과하면 멀미가 난다.

## 공간 규약 (여기서 확정하고 이후 고정)

| 항목 | 값 | 근거 |
|---|---|---|
| 셀 크기 | **3.0m** | 4m는 넓어서 안 무섭고, 2m는 답답해서 조작이 불편하다 |
| 벽 높이 | **3.2m** | 폭보다 살짝 높아야 압박감이 생긴다 |
| 카메라 높이 | **1.6m** | 사람 눈높이 |
| 격자 → 월드 | `(gx, gy)` → `(gx * 3.0, 0, gy * 3.0)` | 프로토타입의 `GRID[y][x]`를 그대로 승계 |
| 벽/통로 표기 | `'#'` = 벽, `'.'` = 통로 | 프로토타입 유지 |

## 완료 기준

- [ ] **팀 3명 중 2명 이상이 스크린샷을 보고 "무섭다"고 답한다** ← 주관적이지만 이게 진짜 기준이다
- [ ] 통합 그래픽(내장 GPU) 1080p에서 **60fps** 유지
  - 얼굴 인식이 나중에 GPU를 함께 쓰므로 여기서 여유가 있어야 한다. 60fps를 못 넘기면 후처리를 줄인다
- [ ] 코너를 돌 때 복도 끝 실루엣이 **안개 속에서 서서히** 드러난다
- [ ] 스크린샷을 Unity로 만든 참고 이미지와 나란히 놓고 비교했을 때 납득 가능하다

## 실패했을 때

바로 엔진을 바꾸지 않는다. 순서대로 시도한다.

1. **텍스처와 후처리부터 의심한다.** 대부분의 "웹 그래픽 같음"은 normal map 부재와 후처리 부재에서 온다
2. 그래도 부족하면 **스타일을 전환한다** — 사실적 렌더링을 포기하고 고대비 흑백/실루엣 위주로 간다.
   오히려 더 무서울 수 있고 웹에 훨씬 유리하다. (`아웃라스트`가 아니라 `림보` 방향)
3. 위 둘이 모두 실패해야 엔진 재검토다. 그 경우에도 기획서 §5.3의 하이브리드(얼굴 인식만 브라우저)를 먼저 본다

# S1. 얼굴 입력

## 만들 것

현재 프로토타입(`spikes/kkakkung_3d_face_motion.html`)에 얼굴 입력을 붙인다. **3D는 건드리지 않는다.**
이미 돌아가는 게임 위에서 입력만 검증하기 위해서다.

## 구현 순서

### 1. MediaPipe 연결
```js
import { FaceLandmarker, FilesetResolver } from '@mediapipe/tasks-vision'

const landmarker = await FaceLandmarker.createFromOptions(vision, {
  baseOptions: { modelAssetPath: 'face_landmarker.task', delegate: 'GPU' },
  outputFacialTransformationMatrixes: true,   // ← 머리 자세. 이게 핵심
  runningMode: 'VIDEO',
  numFaces: 1,
})
```
`facialTransformationMatrixes[0].data`가 4×4 행렬이다. 여기서 yaw/pitch/roll을 뽑는다.
얼굴 bbox 면적은 랜드마크의 min/max로 계산한다 (전진/후진 신호).

### 2. One Euro Filter (기획서 §2.2.3)
yaw · pitch · bbox 면적 **각각 독립 인스턴스**로 필터를 건다.
- 시작값: `mincutoff = 1.0`, `beta = 0.007`
- 튜닝 방법: 가만히 있을 때 떨리면 `mincutoff`를 낮추고, 움직임이 굼뜨면 `beta`를 올린다
- **필터 전/후 값을 화면에 동시에 그리는 디버그 오버레이를 반드시 만든다.** 이게 없으면 튜닝이 감이 된다

### 3. 캘리브레이션
시작 시 2~3초 중립 자세를 캡처해 평균을 오프셋으로 저장. 이후 모든 각도는 이 기준의 상대값이다.

### 4. 히스테리시스 게이트 (기획서 §2.2.2)
```js
if (yaw > TRIGGER && armed) { KkakkungDemo.turn('right'); armed = false }
if (Math.abs(yaw) < RELEASE) { armed = true }
```
`TRIGGER = 18°`, `RELEASE = 8°`, 쿨다운 400ms에서 시작한다. **전부 화면에서 실시간 조절 가능한 슬라이더로 노출한다.** 최종값은 계산이 아니라 실측으로 정한다.

### 5. 연속 층 (엿보기)
필터링된 yaw/pitch를 임계값 미만 구간에서 **화면 회전에 직접 매핑**한다.
CSS 프로토타입에서는 `.corridor-world`의 `rotateY`/`translateX`로 근사한다. 정식 구현은 S2에서.

### 6. 폴백
검출 신뢰도가 낮거나 얼굴이 사라지면 **자동으로 키보드 모드로 전환**하고 화면에 명시한다. 조용히 멈추면 안 된다.

## 구현 시 변경 — 임계값 단위를 도(°)에서 정규화 비율로

기획서 §2.2의 임계값은 `18°` / `8°` 였으나, 실제 구현은 **랜드마크 정규화 비율(-1~1, 무단위)** 을 주 신호로 쓴다.

**이유**
- `facialTransformationMatrixes`는 열우선 4×4 행렬이고, 오일러 각 추출은 회전 순서 규약(YXZ/ZYX…)에 따라 결과가 달라진다. **부호 하나만 틀려도 조작이 반대로 뒤집히는데, 그 버그는 카메라 앞에 앉기 전까지 발견되지 않는다**
- 랜드마크 비율은 규약이 필요 없다. 코 끝(1)과 양 볼(234·454)의 상대 거리비이므로 **얼굴 크기·카메라 거리에 자동으로 불변**이고, 계산이 명시적이라 디버깅이 쉽다

행렬 각도(yaw/pitch/roll)는 **참고값으로 화면에 함께 표시**한다. 기획서의 도(°) 기준과 대조해 최종 문서에 둘 다 기록한다.

| 신호 | 계산 | 명령 |
|---|---|---|
| `yaw` | `(dL - dR) / (dL + dR)`, `dL = nose.x - p234.x`, `dR = p454.x - nose.x` | 좌/우 회전 |
| `size` | 랜드마크 bbox 넓이의 제곱근, 캘리브레이션 기준 대비 상대 변화율 | 전진/후진 |
| `pitch` | `(nose.y - (top.y+chin.y)/2) / faceHeight` | 엿보기(연속 층) 상하 |

**방향 반전 토글**을 UI에 넣었다. 카메라 미러링과 랜드마크 좌표계의 조합으로 부호가 뒤집힐 수 있는데, 코드를 고치는 대신 체크박스 한 번으로 확정한다.

## 튜닝 절차

1. `카메라 시작` → 모델 로드 (3.7MB, 첫 실행만)
2. 정면을 보고 `중립 자세 캘리브레이션` (2초 평균을 오프셋으로 저장)
3. 고개를 좌우로 돌려 회전 방향이 맞는지 확인 → 반대면 `회전 방향 반전` 체크
4. **그래프를 보며 `mincutoff` / `beta` 조정**
   - 가만히 있는데 회색(원본) 선이 떨리고 흰색(필터) 선도 따라 떨린다 → `mincutoff` **낮춘다**
   - 고개를 움직였는데 흰색 선이 굼뜨게 따라온다 → `beta` **올린다**
5. 붉은 점선(발동)과 회색 점선(재장전) 위치를 보며 `발동`/`재장전` 임계값 확정
6. `튜닝값 출력`으로 확정값을 로그에 찍어 기획서 §2.2에 기록

## 완료 기준

- [ ] **손을 쓰지 않고 미로를 처음부터 끝까지 완주한다** ← 이 단계의 유일한 진짜 기준
- [ ] 가만히 있을 때 오발동이 30초에 0회
- [ ] 10분 연속 플레이 후 목이 아프지 않다
- [ ] 얼굴을 가렸다 되돌리면 3초 안에 정상 복귀한다

# S2. 통합 — 3D + 얼굴 입력 — ✅ 통과

**산출물**: `spike-play.html` (단일 파일). Vite/TS 구조화보다 **먼저** 단일 파일로 합쳐 검증한다.
S0의 렌더러와 S1의 입력이 각각 검증됐으므로, 이 단계가 확인할 것은 **둘을 동시에 돌렸을 때의 문제**뿐이다.

## 이 단계에서만 확인 가능한 것

### 1. GPU 경합 — 최대 관심사
얼굴 추론과 WebGL이 같은 GPU를 쓴다. 기획서 §6에 '중' 위험으로 올려둔 항목이며, S0·S1을 따로 돌려서는 절대 드러나지 않는다.

- **추론 30fps / 렌더 60fps로 분리**한다. 추론은 `dt` 누적으로 스로틀링
- 두 fps를 **화면에 나란히 표시**한다. 한쪽이 무너지면 즉시 보인다
- 렌더가 60을 못 지키면 순서대로: 후처리 끄기 → 그림자 끄기 → 추론을 15fps로

### 2. 연속 층의 정식 구현 (기획서 §2.2.1)
S1에서는 CSS transform으로 근사했으나, 여기서 **실제 카메라 회전**이 된다.

핵심은 **보간**이다. 신호는 30fps로 갱신되는데 렌더는 60fps이므로, 목표값(`peekTarget`)을 두고 매 렌더 프레임 지수 보간으로 따라가게 한다. 이 보간이 없으면 30fps 계단이 그대로 보이고, One Euro로 지터를 잡아놓은 의미가 사라진다.

```js
const lerp = 1 - Math.pow(0.001, dt);          // 프레임레이트 독립
peekNow.yaw += (peekTarget.yaw - peekNow.yaw) * lerp;
```

### 3. 얼굴 텍스처 (기획서 §2.4)
웹캠을 오프스크린 캔버스로 **랜드마크 bbox 기준 크롭 → 그레이스케일·콘트라스트** 처리해 그것의 머리 앞면 평면에 붙인다.

- `MeshStandardMaterial`을 쓴다. **손전등이 비출 때만 얼굴이 드러난다** — 이게 §2.3 조우 3단계 연출과 맞물리는 지점이다
- `MeshBasicMaterial`이면 어둠 속에서도 얼굴이 빛나 버려 공포가 무너진다
- 크롭·거울반전·필터는 캔버스 단계에서 처리한다. 셰이더 불필요

## 실측 결과 — 추론 비용과 스레드 결정

| 항목 | 측정값 |
|---|---|
| 추론 소요 (`detectForVideo`, 메인 스레드) | **16~20ms** |
| 블렌드셰이프 끈 뒤 | 거의 변화 없음 — 비용의 대부분이 랜드마크 모델 본체 |
| 프레임 예산 (60fps) | 16.6ms |
| 확정 해상도 배율 | **1.0** |

**즉 추론 1회가 프레임 예산을 넘는다.** 렌더 비용을 0으로 만들어도 추론이 도는 프레임은 구조적으로 밀린다. 초기에 관측된 "매끄럽지 않다"의 기계적 원인이 이것이다.

### 결정 — 메인 스레드 추론으로 간다

블렌드셰이프를 끄고 해상도 배율을 1.0으로 내린 뒤 **체감상 충분히 매끄럽다고 판단**하여 메인 스레드 추론을 채택한다. `추론 스레드` UI 옵션은 제거했다.

**워커 경로는 보류한다.** `face-worker.js` 를 실제 파일로 분리하고 GPU→CPU 자동 재시도·단계별 실패 보고·준비 타임아웃까지 넣었으나, **워커가 오류 없이 ready 에 도달한 뒤 프레임이 흐르지 않는** 상태에서 원인을 특정하지 못했다. 동작하지 않는 경로를 기본값이나 선택지로 남겨두지 않는다.

> 파일은 지우지 않고 상단에 보류 표시만 남겼다. 아래 조건에 해당하면 다시 꺼낸다.

### 재검토 조건

다음 중 하나가 발생하면 워커 분리를 다시 시도한다. 프레임 예산은 앞으로 줄어들기만 한다.

- **S3** — 술래 AI·경로탐색·사운드가 붙어 메인 스레드 작업이 늘어난다
- **S5** — 네트워크 동기화가 메인 스레드에 추가된다
- 저사양 기기에서 추론이 25ms 이상으로 측정된다
- 주기적 히칭이 플레이 중 눈에 걸린다는 피드백이 나온다

### 되살릴 때 먼저 확인할 것

보류 원인이 "ready 는 오는데 프레임이 안 온다" 였으므로, 프레임 공급 경로부터 본다.

1. 워커가 `sig` 메시지를 아예 안 보내는지, 보내는데 메인이 못 받는지 (워커 안에서 `console.log` 확인)
2. **복제 트랙 전송이 실제로 유효한지** — `clone()` 한 트랙을 transfer 했을 때 `readyState` 와 `muted` 상태
3. `MediaStreamTrackProcessor` 경로를 버리고 **bitmap 펌프만으로** 먼저 성공시킬 것 (변수가 하나 줄어든다)
4. `OffscreenCanvas` 2d 에 `VideoFrame` 을 `drawImage` 할 때의 색공간·크기 처리

| | 이전 | 지금 |
|---|---|---|
| 진입점 | `spike-play.html` 단일 파일 | `index.html` + `src/main.ts` |
| 의존성 | CDN URL 이 파일마다 박혀 있음 | `package.json` 한 곳 |

### 개발과 배포의 접속 주소

- **개발** — Vite(5200)가 클라이언트, `serve.ts`(5199)가 Colyseus. 오리진이 갈린다.
  프록시는 두지 않았다 — Colyseus 의 WS 경로가 `/{processId}/{roomId}` 라 접두사 프록시가 안 되고,
  매치메이킹 HTTP 는 Colyseus 가 **CORS 헤더를 이미 붙여준다**(실측). 그래서 클라이언트가 5199 로 직접 붙는다
- **배포** — `npm run build` 후 `serve.ts` 가 `dist/` 를 내보낸다. 정적 파일과 Colyseus 가
  같은 포트라 `location.host` 하나로 끝난다

`src/main.ts` 의 `mpEndpoint()` 가 `import.meta.env.DEV` 로 이 둘을 가른다.

### TypeScript 가 실제로 잡은 것

- **`onLeave(client, consented)` 의 두 번째 인자 타입** — 선언은 `number`, 런타임은 `boolean`.
  `@colyseus/core` 소스를 열어 `code === Protocol.WS_CLOSE_CONSENTED` 로 넘기는 걸 확인하고
  둘 다 받게 좁혔다. 그대로 뒀으면 재접속이 조용히 안 됐을 수도 있는 자리다
- **술래 힌트에 좌표가 없다는 것** — `nettest` 가 런타임에 확인하던 §4.3 ② 규칙이
  이제 `SoundHint` 타입으로 **컴파일 단계에서 보장**된다. 넣으려 하면 빌드가 깨진다
- 튜플 추론, 선택 인자, 콜백 안 대입의 흐름 분석 등 자잘한 것 다수

### 남은 것 — `src/main.ts` 가 아직 1,800줄이다

블록(`/* ══ ... */`)으로는 나뉘어 있지만 한 파일이다. 쪼개지 않은 이유:

- 블록들이 상태를 광범위하게 공유한다 (`GRID`·`player`·`camera`·`SND`·`NET`)
- **순환 참조가 있다** — 소리의 `dread()` 가 네트워크의 `netDread()` 를 부르고,
  네트워크가 소리의 `sting()` 을 부른다
- 화면을 확인할 수 없는 상태에서 한 번에 쪼개면 되돌리기 어렵다

그래서 `tsconfig.client.json` 은 `strict:false` 다. **이건 임시다.**
모듈로 나누면서 하나씩 조인다 — 나누는 순서는 의존이 적은 쪽부터:
`minimap` → `quality` → `audio` → `face` → `net` → `scene`.

## Colyseus 이관 (2026-08-31)

EC2 를 받고 "여러 방 + 모르는 사람도" 로 방향이 정해져 `ws` 직접 구현에서 옮겼다.
방 생명주기·매치메이킹·재접속은 직접 짜면 계속 버그가 나는 영역이다.

**`rules.js` 와 `maze.js` 는 손대지 않았다.** 순수 로직이라 전송 계층을 모르고,
그래서 단위 테스트 360건이 한 줄도 안 고치고 그대로 통과한다. `room.js` 만 교체됐다.

### ⚠️ 버전을 올리지 말 것 — 0.15 로 고정

| | 버전 | |
|---|---|---|
| 서버 | `colyseus@0.15.57` | |
| 클라 | `colyseus.js@0.15.28` | CDN: `.../colyseus.js@0.15.28/+esm` |

- **0.16 라인은 npm 배포가 깨져 있다** — 의존성에 `workspace:^` 가 그대로 남아 `npm install` 이 실패한다 (0.16.1~0.16.5 전부)
- **0.18 서버 + 0.16 클라는 프로토콜이 안 맞는다** — `consumeSeatReservation` 에서 터진다.
  클라이언트 SDK 는 0.16.22 가 마지막이라 0.18 짝이 없다
- 실측으로 확인한 조합이 0.15.57 / 0.15.28 뿐이다

### Schema 를 쓰지 않는다

Colyseus 의 상태 동기화(`@colyseus/schema`)는 **한 방 상태를 전원에게** 보내는 모델이다.
이 게임의 규칙은 정반대다 — 술래는 도망자 좌표를 모르고, 도망자는 탈출구를 모른다 (§4.3 ②③).

그래서 `viewFor()` 로 1인분씩 만들어 `client.send()` 로 보낸다.
**Colyseus 는 방·매치메이킹·생명주기·재접속만 맡는다.**

### 방 두 종류

| | 옵션 | 매칭 | 얼굴 공유 |
|---|---|---|---|
| 공개 매칭 | `code: ''` | 코드 없는 사람끼리 | **금지** |
| 방 코드 | `code: 'ABCD'` | 같은 코드끼리 | 허용 |

`filterBy(['code'])` 가 코드로 방을 가른다. 여기서 두 번 넘어졌다:

1. **`setPrivate(true)` 를 쓰면 안 된다.** 그걸 켜면 방이 매치메이킹에서 통째로 빠져
   **같은 코드를 든 사람조차 못 들어온다.** 대신 코드를 메타데이터에 넣지 않아 목록에서 안 보이게 했다
2. **`code` 를 아예 안 보내면 안 된다.** 값이 없으면 필터가 무력해져 코드 있는 방까지 후보로 잡힌다.
   공개 방은 빈 문자열을 **명시적으로** 보낸다

`filterBy` 는 매치메이킹만 가르므로 `roomId` 를 알아낸 사람이 `joinById` 로 들어오는 경로가 남는다.
얼굴이 오가는 방이라 **`onAuth` 에서 코드를 다시 검사**한다.

### 재접속 — 30초

`allowReconnection(client, 30)`. 와이파이가 끊기거나 새로고침해도 그 안에 돌아오면
**역할·위치가 그대로다.** 토큰은 `localStorage` 에 둔다.

미로를 매 틱 실어 보내던 것을 판마다 한 번(`maze` 메시지)으로 바꿨다.

| `server/maze.js` | 미로 생성 · BFS · 직선 시야 | 네트워크, 타이머, 게임 상태 |
| `server/rules.js` | 기획서 §4 의 규칙 전부 | 소켓, `Date.now()`, 콘솔 |
| `server/KkakkungRoom.js` | Colyseus 방 · 코드 · 얼굴 정책 · 재접속 | 판정 (전부 rules.js) |
| `serve.js` | 정적 + Colyseus 부착 | — |

**시간을 인자로 받는다.** `rules.js` 는 `Date.now()` 를 부르지 않는다.
그래야 5분짜리 라운드를 테스트에서 한 줄로 끝낼 수 있다 — 이게 없었으면
제한시간·쿨다운·페이즈 전환을 전부 손으로 확인해야 했다.

**Colyseus 로 옮겼다.** 처음에는 `ws` 로 직접 짰다 — 방이 하나뿐일 때는 그게 더 단순했다.
EC2 + 여러 방 + 공개 이용으로 방향이 바뀌면서 매치메이킹·재접속이 진짜 기능이 됐다. 위 「Colyseus 이관」 참조.

## 정보 비대칭은 UI 가 아니라 전송에서 막는다

§4.3 ②③ 이 요구하는 "술래는 도망자 위치를 모른다 / 도망자는 탈출구 위치를 모른다" 를
화면에서 가리는 방식으로 구현하면 개발자 도구를 여는 순간 무너진다.
그래서 `viewFor(game, id)` 가 **사람마다 다른 패킷**을 만든다.

- 도망자 패킷: 탈출구 좌표 **없음**. `exitDist`(칸 수)만 → 심장박동 세기가 된다
- 술래 패킷: 도망자 좌표 **없음**. `hints`(상대 방향·거리)만 → 발소리 방향이 된다
- 서로의 모습: **정면 직선 4칸 이내에 벽이 없을 때만** (§1.2 · §2.3)

`server/nettest.js` 가 실제 소켓으로 패킷을 뜯어 좌표가 안 섞였는지 확인한다.

## 실측 — §4.3 ① 추격 성립

`node server/test.js` 가 25판씩 돌린다. 도망자는 막다른 길을 피하며 멀어지고, 술래는 최단경로로 쫓는다.

| 설정 | 포획 | 평균 |
|---|---|---|
| 같은 속도 400/400 | 8/25 | 11.1초 |
| 차등 360/400 | 20/25 | 22.2초 |
| **A안 320/400** (적용) | 20/25 | 13.0초 |

**문서의 우려는 사실이었다.** 다만 360/400 이 포획률은 같고 추격은 1.7배 길어 더 나을 수 있다.
사람으로 실측해 확정한다.

## 미로 — 완전미로를 쓰지 않는다

재귀 백트래커로 완전미로를 만든 뒤 **막다른 칸의 72% 를 뚫어 고리를 낸다.**
완전미로는 술래잡기에 최악이다 — 도망자가 막다른 길에 들어가는 순간 게임이 끝난다.
고리가 있어야 "돌아서 빠져나간다"는 선택지가 생기고, 그때부터 추격이 게임이 된다.

| 크기 | 통로 칸 | 그릴 벽 | 탈출구까지 평균 | 최단 주파 |
|---|---|---|---|---|
| 13×13 | 76 | 88 | 29칸 | 12초 |
| **19×19** (적용) | 172 | 180 | 50칸 | 20초 |
| 23×23 | 250 | 270 | 60칸 | 24초 |

19×19 로 키우면서 **벽을 `InstancedMesh` 로 묶었다** — 180개를 개별 메시로 두면
손전등 그림자가 매 프레임 그 전부를 다시 그린다. 지금은 드로우콜 1개다.

## 확정 값

| 항목 | 값 | 근거 |
|---|---|---|
| 쿨다운 | 술래 320ms / 도망자 400ms | §4.3 ① 실측 |
| 포획 | 1칸 거리 즉사 | §2.3 `contact` |

## 자동 품질 조절

팀원마다 노트북이 달라서 기본값 하나로는 맞출 수 없다. 프레임을 재서 스스로 내려간다.

**병목을 구분하는 게 핵심이다.** `추론 ms` 가 14를 넘으면 메인 스레드가 막힌 것이라
화질을 깎아도 나아지지 않는다 — 이때는 추론 주기(20→최저 10fps)를 먼저 줄인다.
그 외에 프레임이 길면 GPU 문제이므로 해상도 → 그림자맵 → 후처리 → 그림자 순으로 내린다.

2.5초에 한 칸, 회복은 15초 이상 여유로울 때만. 프레임 13~22ms 구간에서는 아무것도 하지 않는다 —
화질이 오르내리는 게 렉보다 거슬리기 때문이다.


> 기계로 검증했다. 로비 UI, 배너, 상대가 보이는 모습, 미니맵 가독성은 눈으로 봐야 한다.
